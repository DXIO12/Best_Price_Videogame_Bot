**The repo root is the import root, and `application/` is a package.** Every internal
import is absolute and `application.`-prefixed (`from application.bot.bot import ...`,
`from application.shops.amazon import ...`), so `price-bot/` — not `application/` — is
the directory that has to be on `sys.path`. The entry point is
`python -m application.gui.main_window`, PyInstaller is pointed at
`application/gui/main_window.py`, and `project_tests/` prepends the repo root to
`sys.path` before importing anything from the app.

**Code lives under `application/`; everything the app writes does not.**
`logs/`, `.env`, `venv/` and `dist/` stay at the repo root, which is what
`config.runtime_config.base_dir()` resolves to (and, in a packaged build, the
directory next to the executable). The one exception is `tracker.db`, which
`database/db.py` places next to its own module.

## File Descriptions

### `application/bot/`

The headless bot package. Runs independently of the GUI on a schedule.

| File | Description |
| ------ | ----------- |
| `__init__.py` | Marks `bot/` as a Python package so it can be imported as `bot.bot`. |
| `bot.py` | Main bot entry point. Loads settings from the DB, scrapes all product URLs on a schedule (APScheduler), compares prices against targets, and hands any hit to `notifications.send_to_enabled()`. Contains `check_prices()`, `_scrape()`, `should_notify()`, `send_notification()` and `save_shop_record()`. |
| `config.json` | Legacy reference file. Bot settings are now read from the `Setting` table in the DB (configured via the Settings Bot dialog in the GUI). This file is no longer used at runtime. |

---

### `application/notifications/`

How an alert reaches a person. One module per channel, the same way one module per shop lives
in `shops/`; nothing outside this package imports a channel directly.

| File | Description |
| ------ | ----------- |
| `__init__.py` | The registry and the only call the bot makes: `send_to_enabled(alert)`, plus `available_channels()`, `get_channel()` and `enabled_keys()`. Channels are listed as explicit imports rather than discovered with `os.listdir()`, so PyInstaller's import analysis finds them and they need no `--add-data`. Returns True when at least one channel accepted the alert; a channel that raises is logged and skipped, never taking the pass down with it. |
| `channel.py` | The contract each channel implements (`KEY`, `CREDENTIAL_FIELDS`, `is_available()`, `load_credentials()`, `is_configured()`, `send()`) and the `Alert` dataclass. The alert is passed **structured, not pre-rendered**: Telegram wants one flat message, a desktop toast a title plus body, an email a `Subject`. |
| `telegram.py` | Telegram Bot API channel (was `bot/notifier.py`). Credentials resolve from the `Setting` table first and the `TELEGRAM_*` environment variables second. Enforces a 10 s timeout and redacts the bot token from every error message. `send_message()` is exposed separately from `send()` for the Settings dialog's *Test* button, which must send with the credentials **typed** rather than the ones stored. |

### `application/config/`

Runtime execution-mode helpers. Depends only on the stdlib and `database`, so any
package (GUI, bot, shops, resolvers) can import it without creating a cycle.

| File | Description |
| ------ | ----------- |
| `__init__.py` | Package marker. |
| `runtime_config.py` | Resolves the effective `debug_mode` flag (`PRICE_BOT_DEBUG` env → DB `Setting.debug_mode` → `config.json` → frozen default) and applies its two effects: `resolve_headless()` for Playwright, and `init_runtime_mode(process)` for the console + log setup. Owns the *paths*: `base_dir()` (repo root in dev, next to the executable when frozen), `config_json_path()`, `log_dir()` and `log_file_path(process)`. Entry points pass their own name — `init_runtime_mode("gui")` / `("bot")` — which is what picks the log file. |
| `logger.py` | Owns the *handlers*. `get_logger("<area>")` returns the `price_bot.<area>` logger every module writes through; `setup_logging()` attaches a `RotatingFileHandler` (1 MiB × 3 backups) plus a console handler, and redirects `sys.stdout` / `sys.stderr` into the logger so third-party output still reaches the file. Also `install_excepthook()`. Deliberately imports nothing from the app — it is handed the path it should write to, which is what lets `runtime_config` import it without a cycle. |

**The level lives on the handlers, not on the logger — the console and the file want
different things.** The console always shows everything: a terminal is open precisely
to watch a pass run. The *file* is what `debug_mode` filters — a release run writes
`INFO` and above, a debug run writes everything. The per-shop narration
(`Scraping Amazon…`, `54.9€ — above target.`, `already has URL, skipping`,
the parallel `[ 1/73]` counter) is all `DEBUG`, so it stays on screen but never
reaches a release log file — that chatter was ~70% of the old log's volume.

Putting the level on the logger instead ties the two together, and since `debug_mode`
*also* decides whether Playwright runs headless, a readable terminal would cost four
visible Chromium windows. `INFO` keeps
the story worth reading later: alerts, best prices, resolved URLs, and the changes the
user makes in the GUI. `WARNING` is "you should know, but nothing crashed" (no URL set,
no scraper, a search that did not render); `ERROR` is failures and unhandled exceptions.

Two formats on purpose: the console gets the bare message, so a terminal session reads
exactly like the old `print()` output, while the file gets `timestamp level [logger]`.
Separators and blank lines are console-only — a timestamped file does not need them.

Environment overrides: `PRICE_BOT_LOG_DIR` moves the whole directory (this is how a
test harness stays out of the real log — importing `application.gui.main_window` runs
`init_runtime_mode` at module level), and `PRICE_BOT_PROCESS` names the process for
helpers that do not pass one, such as `init_db`.

### `application/language_selector/`

Interface translations. Every user-facing string comes from here through
`tr("<section>.<key>")` — console and log output is deliberately left in English,
since diagnostics are easier to compare when they read the same everywhere.

| File | Description |
| ------ | ----------- |
| `__init__.py` | Re-exports the public API: `tr`, `set_language`, `get_language`, `available_languages`, `init_language`. |
| `translator.py` | Loads the JSON catalogs and resolves the active language. Order (first wins): `PRICE_BOT_LANG` env → DB `Setting.language` → `config.json ["language"]` → system locale (only if a catalog exists for it) → `en`. Lookups fall back active catalog → English → the key itself, so a missing or malformed entry never raises inside a Qt slot. |
| `languages/en.json` | Reference catalog (source language). |
| `languages/es.json` | Spanish catalog. |

**Adding a language — no code change required.** Copy `en.json` to
`languages/<code>.json` (e.g. `fr.json`), set `_meta.name` to the name that should
appear in the dropdown (e.g. `"Français"`), and translate the values. It shows up
in Settings → Application → Language on the next launch. Keys you leave out fall
back to English one by one, so a partial translation is perfectly usable.

Placeholders such as `{count}` or `{product}` are named, not positional, so a
translation is free to reorder them — just keep the same names.

Catalogs are searched in two places, external first: a `languages/` folder next to
the executable (or the repo root), then the bundled one. That means a packaged
build can gain a language, or override a shipped one, without rebuilding.

### `application/gui/`

PyQt6 desktop application.

| File | Description |
| ------ | ----------- |
| `__init__.py` | Package marker. |
| `main_window.py` | Main application window. Title row: "Game Price Tracker" plus a gear `QToolButton` in the top-right corner that opens the Settings dialog (`icons.settings_icon()`, like every other icon in the window). Renders the product table (Product, Platform, Target Price, Shops, Best Price). Toolbar: Add, Delete, Modify Product. The table's pinned first row carries the two table-wide actions, each sitting over the column it acts on: a sync icon centered on the Shops column that resolves the URLs still missing (`icons.sync_icon()`, 72×22 px), and a "＋" spanning the edit + delete columns that opens Add Product (`QSizePolicy.Expanding`, so it fills whatever width the two `ResizeToContents` columns happen to have). Both cap their height at 22 px because the pinned row is 24 px. The sync button is disabled while a resolution pass runs: `load_products()` destroys and recreates it, so the state lives on `_resolver_busy` and is re-applied by `_set_add_row`, toggled by `_set_resolver_busy()` from `start_resolver_worker` / `on_resolver_finished` / `on_resolver_error`. The 5-minute `RetryWorker` has its own `on_retry_error` for exactly this reason — sharing `on_resolver_error` would let a background retry failure unlock the button mid-pass. Bottom row: Start · Pause · Stop Bot (centered), each an icon plus a label; while paused the first two read Restart and Continue instead. Pause suspends a running check in place (it parks at the next product/shop boundary and Continue carries on from there) or freezes the between-checks countdown; `_update_bot_buttons()` decides all three buttons' icon, label and enabled state. If Start Bot is pressed without settings configured, opens the Settings dialog first. Drives the retry timer (`QTimer` every 5 min) and updates Shops cells incrementally as URLs resolve. |
| `add_product_dialog.py` | Dialog to add a new product. Lets the user pick platforms, set a target price, and either auto-resolve shop URLs or enter them manually via `ManualUrlDialog`. Prints a summary to the terminal on save. |
| `bot_worker.py` | `QRunnable` that calls `check_prices()` from `bot.bot` in a background thread. Emits `started`, `finished`, and `error` signals to keep the GUI responsive. Carries the `stop_event` / `pause_event` pair the main window uses to cancel or suspend a running check. |
| `icons.py` | Every icon the GUI uses, as Material SVG paths kept inline as Python bytes — no image assets, so nothing to add to the PyInstaller `--add-data` list. `render_svg_icon()` rasterises one to a `QIcon` (`QSvgRenderer` + `QPainter` onto a transparent `QPixmap`) and is `lru_cache`d, so each icon is drawn once per process; named accessors (`edit_icon()`, `settings_icon()`, `play_icon()`, `pause_icon()`, `stop_icon()`, `restart_icon()`, `sync_icon()`) wrap it. `restart_icon()` (single circular arrow, Restart Bot) and `sync_icon()` (double arrow, resolve URLs) are deliberately different glyphs so two unrelated actions never look like the same one. **Nothing here may run at import time** — a `QApplication` must exist first, which is why they are functions and not module-level constants. The module docstring holds the colour vocabulary: grey `#9e9e9e` neutral, green `#4caf50` for "make it go", red `#cc3333` reserved for destructive actions only. |
| `delete_product_dialog.py` | Dialog to select and delete a product and all its associated `ProductShop` rows. Prints deleted product/platform info to the terminal. |
| `modify_product_dialog.py` | Dialog to edit an existing product's name, platforms, target price, and shop configuration. Columns: Modify (checkbox), Product, Platform, Shops, Target Price. The Shops button opens `ShopManagerDialog`. Changes are staged in memory and only written to the DB when "Apply Changes" is clicked. |
| `settings_bot.py` | `SettingsBotDialog` — window titled "Settings", opened from the gear button. Two tabs: **Bot** (check interval, notify-only-best-price, repeat notifications, repeat cooldown in minutes) and **Application** (language, parallel scraping, max parallel workers, debug mode). The language `QComboBox` is populated from whatever catalogs exist in `language_selector/languages/`, and saving applies the new language immediately — the main window relabels itself via `MainWindow._retranslate_ui`, and the dialogs pick it up on their next open. Each field has a circular ℹ button with a description popup. The repeat-cooldown field is disabled when repeat notifications are off, and the workers field when parallel scraping is off. Save writes all fields to the `Setting` DB table and mirrors them to `config.json`. Supports `auto_start=True` mode (button label becomes "Start Bot") used when the user launches the bot without prior configuration. |

### `launcher/`

Scripts to start or stop the project without needing to know the Python environment details,
plus the desktop-launcher installers. They activate the repo-root `venv/` and stay at the
**repo root** — that is the import root, since every internal import is absolute and
`application.`-prefixed. They do not descend into `application/`.

All four start/stop scripts export `PRICE_BOT_PROCESS`, which names the log file, so the
`init_db` step lands in the same log as the app it is about to start instead of a stray
`price_bot_app.log`.

| File | Description |
| ------ | ----------- |
| `start_gui.sh` | Linux/macOS — activates `venv/`, restricts `.env` to owner-only (`chmod 600`), runs `python -m application.database.init_db`, then launches the GUI with `python -m application.gui.main_window`. Browsers follow the `debug_mode` setting; nothing is forced. |
| `start_gui.bat` | Windows equivalent. Uses `icacls` to restrict `.env`. |
| `start_bot.sh` | Linux/macOS — same setup, then the headless bot (`python -m application.bot.bot`) with `PRICE_BOT_DEBUG=0` / `PRICE_BOT_HEADLESS=1`. |
| `start_bot.bat` | Windows equivalent. |
| `stop_bot.sh` | Linux/macOS — finds the bot by command line with `pgrep -f`, then **confirms each candidate is a python process** before signalling it. The check is load-bearing: `pkill -f` tests its pattern against every command line on the machine, and a bare `pkill -f "bot.bot"` will kill the shell running the script and still report success. |
| `stop_bot.bat` | Windows equivalent via `Get-CimInstance Win32_Process`, filtered on `Name -like 'python*'` for the same reason, and excluding PowerShell's own PID. Exits with the number of processes stopped, so the caller's `%errorlevel%` reflects what happened — reading `powershell.exe`'s own exit code always reported success. |
| `price-bot.desktop.in` | Template for the Linux desktop entry. `@REPO@` and `@ICON@` are substituted at install time. Declares two `Desktop Action`s so one menu entry covers all three scripts: left click opens the GUI, right click offers headless start/stop. |
| `install_launcher.sh` | Installs that entry into `~/.local/share/applications/`, the icon into the hicolor theme, and refreshes the menu caches. `--uninstall` reverses it. |
| `install_launcher.ps1` | Windows — creates a Start Menu shortcut (`-Desktop` adds one on the desktop, `-Uninstall` removes them). Targets `venv\Scripts\pythonw.exe` directly rather than `start_gui.bat`, which would flash a console window on every launch; debug mode still gets a console because `_attach_windows_console()` allocates one when none is attached. Runs `init_db` and the `icacls` hardening once at install time, since bypassing the `.bat` bypasses those too. |

### `packaging/`

PyInstaller packaging scripts and the icon generator. Kept apart from `launcher/` because they
produce a build, they don't run the app.

Named `packaging/`, not `build/`, for two concrete reasons: `build` is PyInstaller's own default
`--workpath`, so a build dropped its temporary tree straight onto these scripts; and
`.gitignore` lists `build/` under build artifacts, which silently hid any new file added here.

| File | Description |
| ------ | ----------- |
| `build_exe.sh` | Linux/macOS — builds `dist/price_bot_gui/` from `application/gui/main_window.py`. Regenerates the icons, then **stages a copy of `application/` with every `*.db` stripped** and bundles that via a single `--add-data`. The staging matters twice over: the source tree has to ship as data because `add_product_dialog.get_available_shops()` lists `shops/*.py` at runtime and `translator.py` globs `languages/*.json`, and `application/database/tracker.db` is the *live* database — an earlier version of this script deleted it before building. |
| `build_exe.bat` | Windows equivalent; stages with `robocopy /XF`. |
| `make_release.sh` | Zips `dist/price_bot_gui/` into a single file to hand over, with `DISTRIBUTION_README.md` copied in as `LEEME.md`. Refuses to package a build containing a `*.db` or a `.env` — both accumulate in `dist/` from running the build output, and either would hand a tester someone else's data or a live bot token — and refuses if `browsers/` is missing. |
| `DISTRIBUTION_README.md` | The end-user guide that travels inside the zip. Written for someone who has never seen the project: open it, connect Telegram, add games. |
| `make_icons.py` | Renders `assets/price-bot.svg` to `price-bot.png` (256px) and a multi-size `price-bot.ico` (16→256). Uses `QSvgRenderer` plus Qt's PNG writer, like `gui/icons.py`, so no new dependency; the ICO *container* is assembled by hand with `struct` because Qt's ICO writer stores only one image, and a single-size icon looks blurry in the Windows taskbar. Run automatically by both build scripts. |

Note: `playwright install chromium` must be run on the target machine separately — the browsers
are ~150 MB and are not bundled. The `.env` must also sit next to the executable, because
`find_dotenv()` uses the working directory when `sys.frozen` is set instead of walking up from
the calling source file.

### `application/services/`

Business logic that sits between the GUI and the scrapers/resolvers.

| File | Description |
| ------ | ----------- |
| `product_service.py` | CRUD helpers for `Product` and `ProductShop` DB rows (create, read, update, delete). |
| `resolve_urls_service.py` | Orchestrates URL resolution for a product: iterates available shops, calls the right resolver, writes the URL to `ProductShop`, and schedules retries on failure (`retry_count`, `next_retry_at`). Also exposes `retry_due_shops()` for the periodic retry timer. **The retry ladder applies only to `SEARCH_FAILED`** — a `NOT_FOUND` or `ONLY_USED` answer from the shop goes straight to the exhausted sentinel via `_mark_terminal()`, since re-running an identical search can only produce an identical answer. The "Update URLs" button still re-runs those rows (it skips only rows that already hold a URL), so a terminal verdict is never a dead end. Resolutions in flight are claimed in `_inflight` (guarded by `_inflight_lock`): saving a product, the "Update URLs" button and the retry timer can all target the same row at once, and without the claim each one would scrape the shop again and re-write the same URL. |
| `resolver_worker.py` | Two `QRunnable` workers: `ResolverWorker` (first-time resolution, emits `progress` signals per shop) and `RetryWorker` (re-runs failed shops whose `next_retry_at` is due). `finished` carries `{product_id: {shop: ResolutionResult}}`, which the main window turns into the status-bar summary naming the shops that came back `NOT_FOUND` / `ONLY_USED`. |
| `url_search_service.py` | Builds each shop's search URL from a product name + platform (`SHOP_SEARCH_PATTERNS`, `get_search_url()`). `_SHOPS_WITH_PLATFORM_FILTER` (wakkap, xtralife, game) leaves the platform **out** of the query for shops that determine it themselves — on game.es appending it returns zero results. |

#### `services/url_resolvers/`

One resolver per shop. Each takes a search URL and platform string, navigates the shop's search UI with Playwright, scores candidates by word overlap, and returns a `ResolutionResult` — the URL, or *why* there isn't one. **All seven active resolvers are migrated** (2026-08-22); `normalize()` is kept for the gitignored Carrefour / Corte Inglés stubs, which still return a bare `str | None`.

**Read `resolution.py` before adding or editing one.** Three rules it exists to enforce:

1. A resolver must never fall back to "the closest thing I saw" — that is how searches for Ninja Gaiden Ragebound resolved to Minecraft and to Naruto x Boruto.
2. When it cannot tell "the shop has nothing" from "the page never loaded" it must report `SEARCH_FAILED`: a needless retry costs one browser run, a wrong terminal verdict stops the shop being tracked at all.
3. **Pick the product by name across the whole page first, then filter by platform** — never the other way round (`is_best_available_match`). Filtering first hides the evidence that would reject a near-miss: with only Switch cards left, plain "Hollow Knight" is the best remaining answer to "Hollow Knight Silksong" and scores 0.67, comfortably over the floor. This is also why the shops' own platform facets are deliberately **not** applied in the Wakkap and Xtralife resolvers.

| File | Description |
| ------ | ----------- |
| `amazon_url_resolver.py` | Searches Amazon.es and scores `[data-component-type="s-search-result"]` tiles on name, platform, condition and bundle before taking one; `clean_amazon_url()` reduces the href to `<slug>/dp/<ASIN>` and strips the `/-/en/` locale prefix a headless context often lands on. Two Amazon-specific traps: its search **500s on a percent-encoded colon** (`?k=Onimusha%3A+…` renders "Lo sentimos" with zero tiles), stripped by `_sanitise_search_url()`; and its titles frequently name **no platform at all** ("Onimusha Way of the Sword"), so the rule is `mentions_any_platform()` — reject a title naming a *different* console, accept one naming none, rank explicit matches first. |
| `game_url_resolver.py` | Reads the Game.es **results page** at `/buscar?q=<hyphen-slug>` — *not* the header autocomplete, which pads no-match queries with unrelated best-sellers and hides second-hand listings. (`/buscar?text=`, the URL `url_search_service` builds for display, renders the homepage.) Cards are `div.search-item`; link and clean title come from `a.figure` / `data-list-item-name`. Waits on `div.search-list.search-completed` or it reads unhydrated skeleton cards. Scores `matched − extra` word overlap above `MIN_TITLE_MATCH_RATIO`, filters second-hand into `ONLY_USED`, and visits tied pages to pick the cheapest. |
| `mediamarkt_url_resolver.py` | Navigates straight to the MediaMarkt.es search URL and scores `article[data-test="mms-product-card"]` by name overlap + platform. The results grid (`[data-test="mms-search-srp-productlist"]`) rendering is what separates `SEARCH_FAILED` from `NOT_FOUND`. The pre-2026-08-21 anchor selector `mms-router-link-product-list-item-link` no longer exists in the site's markup. Rejects `is_bundle` titles, which is what stops "Mario Kart World" resolving to *Consola portátil Nintendo Switch 2 Mario Kart World 256 GB*. |
| `pccomponentes_url_resolver.py` | Searches PCComponentes.com and matches the `data-product-name` attribute on **both** name (`title_match_ratio`) and platform — a platform-only test let any Switch game satisfy any Switch search. Card wait uses `state="attached"`: the first of ~71 cards sits in a collapsed panel, so the default "visible" wait times out on a fully rendered page. |
| `todoconsolas_url_resolver.py` | Types into the TodoConsolas.com search box, then ticks the `Regiones de juegos → PAL/ES` and `Estado → Nuevo` facets (second-hand only when no new copy is offered). Its search overlay lives in a shadow root, so every read goes through Playwright locators. Platform comes from the product URL category slug (`PLATFORM_SLUGS`), since the shop has no platform facet. **A missing region facet is not "no PAL/ES stock"** — the shop renders a facet only when its results split on it, so an all-Spanish result set offers none; the `(SP)`/`(UK)` title suffix read by `_title_region` is the fallback. `[data-test="no-results-info"]` is its empty state, and is what separates `NOT_FOUND` from `SEARCH_FAILED` here. |
| `wakkap_url_resolver.py` | Searches Wakkap.com. Cards are plain `<div>`s carrying no href, so the URL only exists after clicking — the winner is chosen from the read-only card data first, and exactly one card is clicked. Platform comes from each card's own `div.tag-name` badge ("Switch", "NSW2", "PS5", "Xbox Series"); the site's platform dropdown is **deliberately unused** (it was keyed on the GUI names `"ns"`/`"ns2"` while resolvers receive the DB names, so it never applied to a Nintendo product — and letting the shop pre-filter blinds `is_best_available_match`). |
| `xtralife_url_resolver.py` | Navigates Xtralife.com and scores up to 40 `/producto/` cards. Platform and department both come from the card subtitle ("Switch 2 Edición Estándar", "Libros Edición Estándar"), with the URL slug as fallback; `div.digitalFlag` is the only thing separating the download code from the boxed copy, since neither title nor URL says so. The site's Plataforma facet is **deliberately unused**, for the same reason as Wakkap. |
| `resolution.py` | Shared vocabulary, not a shop. `ResolutionStatus` (`RESOLVED` / `NOT_FOUND` / `ONLY_USED` / `SEARCH_FAILED`), the `ResolutionResult` dataclass, `normalize()` for legacy returns, and the matching helpers every resolver should use.<br><br>**Identity:** `title_match_ratio` + `MIN_TITLE_MATCH_RATIO` (0.6) is a floor, not a decision — it cannot separate a game from its own sequel (`"Hollow Knight"` scores 0.67 against a Silksong search). `best_relevance()` / `is_best_available_match()` add the page-wide comparison that can.<br>**Platform:** `platform_matches_title` rejects a "Switch 2" title for a "Switch" search (the older console's name is a prefix of the newer one's); `mentions_any_platform` covers shops whose titles name no console; `slug_as_text` lets a URL be read as words so the same tests apply to it.<br>**Condition and shape:** `is_used`, `is_digital`, `is_bundle` (a pack or a console-with-game matches every query word by construction and cannot be rejected by scoring).<br>**Ranking:** `ranking_score` = matched − extra, with `IGNORED_QUERY_WORDS` dropped from *both* sides so a title is not penalised for naming its console.<br><br>Matching is whole-word, not substring (`_alias_present`) — "nsw" is inside "answer" and is also the prefix of "nsw2". `normalize_words` folds accents via NFKD: the old `[^a-z0-9\s]` did not drop a letter, it split the word around it ("ensueño" → `{"ensue", "o"}`). |
